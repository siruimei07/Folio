# ADR-0001: Application stack

- **Status:** Accepted (Sirui, 2026-09-26)
- **Date:** 2026-09-26
- **Deciders:** Sirui Mei
- **Inputs:** [`docs/product/brief.md`](../product/brief.md) (Chinese, §12 lists the constraints),
  [`docs/specs/system-overview.md`](../specs/system-overview.md). Versions and facts were checked
  against primary sources on 2026-09-26.

## Context

Folio is a desktop document library for **Windows 10/11 only** (decided 2026-09-26). A future
macOS version, if any, would be a separate Swift app. It must read and write the same iCloud
remote, and would ideally reuse Folio's core logic.

The system has three layers (system overview §2): an untrusted web UI, a thin privileged shell,
and a core library. The core owns scanning, watching, the catalog, versioning and sync. Forces on
the stack, in priority order:

1. **Data safety.** Versioning and sync bugs lose user files, the worst possible outcome. The core
   needs strong typing, deterministic tests and property tests.
2. **UI quality.** The visual reference is GitButler (a web UI). Previews rely on JavaScript
   renderers (pdf.js, Office renderers, KaTeX, a syntax highlighter), so the UI needs a
   Chromium-class engine. It must also feel native on Windows 11: title bar, snap layouts, and
   drag and drop with Explorer.
3. **Core workload.** Libraries hold up to 50k files / 100 GB. The core must:
   - watch the library recursively and hash files incrementally;
   - extract text and run SQLite full-text search (Chinese needs trigram matching);
   - keep a content-addressed version store;
   - handle iCloud placeholders (Windows Cloud Files API), the Recycle Bin and Credential Manager.
4. **Testability.** Every user flow gets a Playwright e2e test (CLAUDE.md §4.2).
5. **Maintenance budget.** One owner plus AI agents; upkeep that only preserves the status quo
   must stay small.
6. **Distribution.** Auto-updates to a few friends without paid code signing.
7. **Future Swift app.** It must at least be able to reimplement the documented remote format,
   and ideally can reuse the core.

Development machine: Node 24.19.0, pnpm 11.25.0, Rust 1.97.1 (`x86_64-pc-windows-msvc`), Visual
Studio 2026 Build Tools with the C++ workload, Windows SDK 10.0.26100, WebView2 Runtime 153.

**Reference signal.** GitButler has two desktop clients in one repository:
- The shipping app is Tauri 2 + Svelte + Rust, with e2e tests in WebdriverIO.
- The next-generation client, "GitButler Lite", is Electron 44 + React 19. It exposes the same Rust
  core through napi-rs and has Playwright e2e tests. The reasons for the switch are not public.

Both clients keep the Rust core and differ only in the shell. The lesson for Folio: keep the core
shell-agnostic, so the shell stays the cheaper decision to reverse.

## Decision

1. **Core.** A Rust library crate, `folio-core`, with no Tauri, UI or IPC types. It reaches the OS
   only through adapter traits (file system, watcher, Recycle Bin, credentials, cloud
   placeholders) that have real and fake implementations.
2. **Shell.** Tauri 2 on the WebView2 Evergreen runtime. Tauri 2.12.0 was released on 2026-09-26;
   pin the latest 2.x patch at scaffold time. The app crate, `folio-app`, is thin: it validates
   input, calls the core, maps errors, emits events and integrates with the OS.
3. **UI.** React 19 and TypeScript, built with Vite. The UI reaches the shell only through one
   `ipc` module, so changing the transport later stays a local change.
4. **IPC contract.** Rust types are the single source of truth for commands, events and the error
   union.
   - The TypeScript bindings are generated by `tauri-specta`. It is still a release candidate, so
     it is pinned to an exact version (`=2.0.0-rc.25`); if it stalls, fall back to `ts-rs`, which
     is stable but generates types only.
   - The generated file is checked in, and CI fails if regenerating it produces a diff.
   - Serde deserialisation gives structural validation; handlers add semantic checks (paths inside
     the library, length limits).
5. **SQLite.** Accessed from the core through `rusqlite` with the bundled SQLite and FTS5. Schema,
   migrations and the query layer are decided in ADR-0002.
6. **Window chrome.** A custom title bar carries the GitButler-style top bar. Windows 11 snap
   layouts come from a native hit-test overlay on the maximize button (spike 4b). If the spike
   fails, fall back to the native title bar with the top bar below it.
7. **Testing.**
   - Core: `cargo test`, with `proptest` for sync and versioning invariants.
   - UI: Vitest + Testing Library.
   - UI in a plain browser: a mocked `ipc` module lets it run there for fast tests and for design
     and accessibility reviews in the browser pane.
   - End to end: Playwright drives the real app over CDP, following Playwright's WebView2 guide.
     Each worker gets its own `--remote-debugging-port` through
     `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` and its own `WEBVIEW2_USER_DATA_FOLDER`.
8. **Packaging and updates.**
   - Installer: NSIS, per user, no administrator rights. MSI is not used because it builds with
     WiX v3, which lost support in February 2025.
   - WebView2: the installer embeds the WebView2 bootstrapper (about 1.8 MB) for the rare Windows 10
     machine without the runtime.
   - Updates: `tauri-plugin-updater` with a minisign keypair. Tauri makes update signatures
     mandatory, and they are free.
     - Enable `requireSignedVersion`; keep `allowDowngrades` off.
     - The update feed is a static `latest.json`.
9. **Pins.**
   - Node 24 LTS (24.19.0): `.nvmrc` plus `engines`.
   - pnpm 11.25.0: `packageManager`.
   - Rust 1.97.1: `rust-toolchain.toml` with `rustfmt` and `clippy`, target
     `x86_64-pc-windows-msvc`. Tauri 2.12 needs Rust 1.90 or newer.
   - Everything else: exact versions in `pnpm-lock.yaml` and `Cargo.lock`, both committed.

## Options considered

### Option A: Electron + React + TypeScript, core in TypeScript

Current release: Electron 44.4.5 (Chromium 152, Node 24.21). A new major arrives every 8 weeks,
and each major is supported for about 6 months.

| Dimension | Assessment |
|---|---|
| Complexity | Low–medium: one language, one toolchain |
| Cost | Free. Installer estimated at 100–120 MB (the Electron 44 runtime zip alone is 158 MB); every update is similar in size |
| Scalability | Adequate: I/O-bound work is fine in Node; CPU work needs worker threads |
| Team familiarity | Highest: TypeScript everywhere |
| Future Swift reuse | None: the Mac app would reimplement versioning and sync |

**Pros**
- One language, and the shared TypeScript contract is trivial.
- Playwright drives the app through `_electron.launch`, the most turnkey option. It is still
  labelled experimental, though (see cons).
- Chromium is pinned by the app.
- Useful built-ins:
  - shell thumbnails through `nativeImage.createThumbnailFromPath`, which uses Explorer's
    thumbnail cache;
  - drag-out through `webContents.startDrag`;
  - `shell.trashItem` for the Recycle Bin;
  - `safeStorage` for secrets (DPAPI).
- Native caption buttons over a custom title bar through `titleBarOverlay`. Microsoft documents
  snap layouts as working since Electron 13.
- SQLite is straightforward: `better-sqlite3` 13 ships Node-API prebuilds, so there is no
  per-Electron rebuild; `node:sqlite` is also available as a release candidate.

**Cons**
- The core cannot be reused from Swift, so there is a real risk of the two apps drifting apart on
  the remote format.
- Win32 APIs such as Cloud Files placeholders and Credential Manager need FFI or native addons.
- Playwright's Electron support is experimental:
  - test builds must keep the `nodeCliInspect` fuse enabled, against Electron's hardening advice;
  - native dialogs have to be stubbed in the main process;
  - it has broken on new Electron majors before.
- Chromium ships inside the app, so staying patched means following a major release every 8
  weeks.
- **Unsigned updates are on a deprecation path.** For Windows builds without Authenticode:
  - electron-updater skips signature verification today; it only checks a SHA-512 served by the
    same feed as the installer;
  - electron-builder v28 will treat the missing publisher as a failure, and no path for unsigned
    apps is documented.

### Option B: Tauri 2 + React + TypeScript with a Rust core (chosen)

| Dimension | Assessment |
|---|---|
| Complexity | Medium: Rust and TypeScript, one runtime boundary |
| Cost | Free. Installer of a few MB; small updates |
| Scalability | High: native core, direct Win32 access |
| Team familiarity | Rust is newer for Sirui; agents handle it well; compile times are longer |
| Future Swift reuse | Yes: `folio-core` can be exposed through UniFFI (0.32, pre-1.0; used in production by Firefox, Element X iOS and Bitwarden) |

**Pros**
- The privileged side is Rust only; there is no Node runtime in the shipped app.
- Direct Win32 access through Microsoft's `windows` crate: the Cloud Files API, WIC for HEIC
  images, `IShellItemImageFactory` thumbnails.
- Mature crates for the rest: `trash` for the Recycle Bin, the `keyring` crate family for
  Credential Manager, `rusqlite` for SQLite.
- Drag-out through CrabNebula's `tauri-plugin-drag`; reveal-in-Explorer through `tauri-plugin-opener`.
- Windows patches WebView2 itself, and keeps doing so on Windows 10 22H2 until at least October
  2028. The browser engine never needs an app-side upgrade treadmill.
- Commands are gated per window by a capability-based permission model.
- Updates are authenticated without Authenticode:
  - update signatures are mandatory, and from 2.12 they can be bound to the version;
  - in-app updates download without the Mark-of-the-Web, so they should not trigger SmartScreen
    again (inference, to verify).
- Small installer.
- GitButler's shipping app proves the stack for exactly this kind of UI.

**Cons**
- Playwright works only over CDP, which Playwright calls "significantly lower fidelity".
  - Tauri's docs recommend WebdriverIO instead, and GitButler's Tauri app uses it.
  - We have to write and maintain our own fixture (spike 4a).
- Snap layouts are not built in when the title bar is custom (Tauri issue #4531, open since 2022).
  - The options are community plugins or a native child window that answers `HTMAXBUTTON` hit
    tests (spike 4b).
  - The fallback is the native title bar.
- The typed-IPC generator is still a release candidate, so it needs an exact pin.
- On Windows, OS file drops (with paths) and HTML5 drag and drop inside the page are mutually
  exclusive. In-app drag and drop has to use pointer events.
- Tauri 3 is in alpha, with runtime selection and an optional CEF (bundled Chromium) runtime. It
  means a migration eventually, and no support window for v2 has been published.
- WebView2 updates under us between our releases, although it rarely breaks anything.

### Option C: Electron + React + TypeScript shell, Rust core through napi-rs

This is the architecture of GitButler Lite.

| Dimension | Assessment |
|---|---|
| Complexity | High: three layers (renderer, Node main process, Rust addon) and two IPC hops |
| Cost | Free; large installer and updates, as in A |
| Scalability | High: native core |
| Team familiarity | Two languages plus Electron's process model |
| Future Swift reuse | Yes, same core as B |

**Pros**
- Keeps B's Rust core and adds Electron's conveniences: `_electron` Playwright, native caption
  buttons, built-ins, pinned Chromium.
- napi-rs generates TypeScript types for the core API.

**Cons**
- More glue code and more build tooling (napi build plus electron-builder).
- Keeps A's burdens: the 8-week Electron treadmill, a 100 MB-class installer, and
  unsigned-update verification that is being deprecated.

Why not now: C's advantages over B are testing convenience and snap layouts, and both have
mitigations in B that spikes 4a and 4b will prove or rule out. C's costs are permanent. C stays as
the **fallback shell**: because the core is shell-agnostic and the UI calls a single `ipc`
module, moving from B to C later replaces the shell and the IPC transport, not the core or the UI.

### Also rejected

- **WinUI 3 or WPF (C#).** The most native look, but a GitButler-style custom UI and the web-based
  preview renderers would still need WebView2 islands. The design pipeline and the Playwright flow
  assume a web UI, and a C# core is not reusable from Swift.
- **Flutter or Qt.** No web renderers for previews, and different design tooling.
- **Svelte instead of React** (GitButler's choice). React has the larger ecosystem for accessible
  primitives, virtualised lists and command palettes. CLAUDE.md §6 already names React.

## Trade-off analysis

| Driver | A | B | C | Notes |
|---|---|---|---|---|
| Data safety (typed, testable core) | ○ | ● | ● | Rust types and property tests in B and C |
| Native feel on Windows 11 | ● | ◐ | ● | B needs native work for snap layouts with a custom title bar |
| Playwright e2e | ● | ◐ | ● | A and C: experimental API but turnkey. B: CDP plus our own fixture |
| Maintenance | ◐ | ● | ○ | A and C ship Chromium; C adds a third layer |
| Distribution without signing | ○ | ● | ○ | Unsigned Electron updates are fail-open today and fail-closed from electron-builder v28 |
| Security posture | ◐ | ● | ◐ | B: no Node runtime, capability-gated commands |
| Future Swift reuse | ○ | ● | ● | Rust core through UniFFI |
| Simplicity | ● | ◐ | ○ | |

● strong · ◐ acceptable with work · ○ weak

The decision rests on data safety, maintenance and distribution, where B is strongest. B's two
weak spots (e2e tests and snap layouts) are exactly what spikes 4a and 4b test early. If either
fails badly, Option C is the planned exit, and it keeps the core and the UI.

Untrusted content is the same problem in every option. Previews render files from the user's
library, and a malicious Markdown, SVG or Office file must not reach the IPC surface. This is
handled by the security baseline (Action item 5), not by the choice of stack.

## Preview renderers (independent of the stack)

All three options render previews in Chromium, so renderers do not change the decision. They do
bound what the product can promise (brief §5.3, "no external software"):

| Format | Candidate | Licence | What to expect |
|---|---|---|---|
| PDF | pdf.js (`pdfjs-dist` 6.x) | Apache-2.0 | Full fidelity |
| Word | `docx-preview` | Apache-2.0 | Continuous flow, no pagination; no charts, SmartArt or TOC fields |
| Word (text only) | `mammoth` | BSD-2 | Text for indexing and diffs; its output must be sanitised |
| Excel | SheetJS CE | Apache-2.0 | Values and number formats **without cell styles**; no maintained open-source renderer reproduces styles |
| PowerPoint | `@aiden0z/pptx-renderer`, `pptx-viewer-core` | Apache-2.0 | Young projects with self-reported fidelity; test with real Chinese decks (spike 4c) |

Avoid `pptx-preview` (closed source) and AGPL renderers such as SuperDoc.

## Consequences

**Easier**
- Native-speed scanning, hashing and sync.
- First-class Win32 integration.
- Small installers and authenticated updates without paid signing.
- A path for a Swift app to reuse the core.
- GitButler's UI patterns carry over directly.

**Harder**
- Two languages and longer Rust build times.
- A custom Playwright-over-CDP fixture.
- Native work for snap layouts.
- An exact-pinned release-candidate code generator to keep up to date.

**Revisit when**
- Tauri 3 becomes stable: plan the migration, and weigh its CEF runtime if a pinned Chromium
  becomes valuable.
- Playwright over CDP proves unreliable: choose between Option C and WebdriverIO. WebdriverIO
  would need a CLAUDE.md change.
- Unsigned builds block friends (see Action item 6).
- Friends need ARM64 builds.

5. [ ] Security baseline:
   - strict CSP (done: the production CSP has no `'unsafe-inline'`);
   - one capability set per window (done: individual permissions only, checked by a test in
     `crates/folio-app/src/ipc.rs`; an e2e test checks that the shell rejects other commands);
   - previews in sandboxed iframes with no IPC access (verify that frames cannot reach Tauri IPC);
     - Result (2026-09-27, lane `spike/core-preview-sandbox`): the preview frame is
       `<iframe sandbox="allow-scripts">` on its own `folio-preview` scheme
       (`crates/folio-app/src/preview.rs`). Its CSP runs only the frame's own scripts (no inline
       handlers, no `eval`) and blocks fetch-class requests (a local server in the e2e test
       receives nothing); the window's CSP allows only that frame source. An e2e test probes from inside the frame: its origin is opaque; markup cannot
       run script; the window's DOM, storage, fetch-class requests, top-level navigation and
       Tauri's IPC are blocked; nothing the frame sends reaches Tauri.
     - No CSP directive covers WebRTC: in the security review it reached the internet and the
       local network from the frame, and no WebView2 flag closed it. The frame removes
       `RTCPeerConnection` before anything renders, and a nested frame cannot hand it back.
     - Two platform facts make these layers necessary. On Windows, wry injects Tauri's IPC
       script, invoke key included, into every frame, and Tauri treats pages of app-registered
       schemes as local, with the window's permissions. The frame's calls fail only because its
       CSP blocks the IPC fetch (Tauri would also reject its `Origin: null`) and WebView2 does not
       deliver frame messages to the handler Tauri listens on. The e2e test fails if a Tauri or
       WebView2 update changes either.
     - So the `sandbox` attribute is load-bearing: in the review, a `folio-preview` page loaded
       without it reached IPC. The scheme therefore serves only the preview page and its built
       assets: it rejects other paths and other HTML, and never falls back to `index.html` (a
       missing asset is a 404). Every response, errors included, carries the preview CSP and
       `nosniff`; the production CSP names no dev-server ancestor; only subresources get CORS.
       Rules for the preview UI: embed
       previews only through one component that sets these flags, and give each file a fresh
       frame, so script from one file never sees the next.
     - Open: under `pnpm dev` the scheme serves the preview page from the last `vite build`
       (`apps/desktop/dist`), not from the dev server.
   - sanitised Markdown and HTML.
